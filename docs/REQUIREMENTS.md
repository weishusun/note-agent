# REQUIREMENTS — 产品需求基准

> 2026-10-11 与使用者逐项确认。后续开发以本文件为准。
> 本文件说的是「要做成什么样」；数据格式和接口仍以 [SCHEMA.md](SCHEMA.md) 为准。
> 两者冲突时，先改 SCHEMA 再动代码，见第 5 节。

---

## 1. 定位

一个**长期使用的个人知识库**：使用者主要在网站上阅读，把看到的内容（截图为主）交给应用，
应用自动整理成笔记、自动分类，之后可以浏览、检索、提问。

- 只在本机使用，单人。
- **只用这个应用**，不依赖 Obsidian。笔记仍存成 Markdown 文件，但查看、编辑、可视化都在应用里完成。
- 规模：按一年后**一两千条**笔记设计。
- 最终形态是**桌面应用（exe）**，不通过浏览器访问。

## 2. 功能需求

### 2.1 录入

| 项 | 要求 |
|---|---|
| 来源 | 截图、短文本、**网页链接**、**PDF 和长文档** |
| 体验 | **连续丢、后台排队**：一口气提交多份，后台依次处理，处理完有提示。慢可以接受，**内容要完整** |
| 长内容 | **摘要级**：一份文档 / 一个网页生成一条主题笔记（摘要加大纲），关键概念各拆成一条概念笔记并互相链接（2026-10-13 确认，和截图录入一致）。不需要答到原文细节。上传的原文件存进知识库（单个不超过 30 MB）；网页只记网址 |
| 重复 | 新内容与已有笔记相似或重复时，新笔记先存下，**把两条笔记在知识库里的内容并排展示**，由使用者选：保留已有的、保留新的、两条都留、合并。先按名字判断（标题与已有笔记的标题或别名相同）；名字没撞上的再按内容：向量找出最接近的已有笔记，由模型判断是不是同一个概念 |
| 补充 | **允许模型用自身知识补充笔记**，补充的部分必须在笔记里单独成段并标明，不与来自资料的内容混排 |

「内容要完整」意味着看图提取保持思考模式开启（实测关闭后会漏内容），速度靠排队来消化，不靠降质量。

### 2.2 笔记形态

两种笔记，互相链接：

- **主题笔记**：一张图 / 一份文档对应一条，**保留原来的整体结构**（流程、表格、层次）。
- **概念笔记**：从中拆出的、值得独立成条的概念，各一条，链接回主题笔记。

理由：三种视图各需要一种东西——图谱要概念作节点，思维导图要层次；流程图被拆成
「A 输出到 B」这类只描述箭头的碎片，也靠主题笔记来避免。

### 2.3 分类

- **固定两层**：大块 → 小块。
- **全自动**：录入时就归类，需要时自动建新的大块或小块，不需要使用者审批。
- **可随时手改**：改分类名、把笔记移到别的块、合并或拆分块。
  **手动改过的地方被锁定**，模型此后不得覆盖。
- 「待整理」只留给模型拿不准的少数笔记，不再是所有笔记的默认去处。
- 现有笔记要能一键重新归类。

### 2.4 浏览与可视化

| 视图 | 内容 |
|---|---|
| 目录树加索引 | 可折叠的大块、小块，带笔记数；选中一块后列出其中的笔记标题和概要 |
| 关系图谱 | 笔记为节点、链接为连线；能按大块筛选（一两千条时全量显示不可用）。范围里超过 500 条时不画，提示先选小一点的范围 |
| 思维导图 | 把一个大块展开成树状图，一眼看到层次。四层：大块 → 小块 → 主题笔记 → 概念笔记；概念笔记挂在同一个小块里链接着它的主题笔记下面，没有的直接挂在小块下，每条笔记只出现一次（2026-10-13 确认） |

三种视图都在「笔记」页里，右上角切换，共用左边的分类目录（2026-10-13 确认）。

### 2.5 问答

- 保留现有的：先检索、带引用作答、没检索到时标明「来自模型自身知识」。
- 新增**多轮追问**：能接着上一个回答继续问，记得上下文。提问页只保留当前这一段对话（刷新不丢，点「新对话」清空），过去的对话不保存（2026-10-13 确认）。

### 2.6 编辑

**完整编辑**：改标题、正文、别名、分类；删除；手写新笔记。全部在应用内完成。

### 2.7 可信度

**去掉「未核实」这个概念**：笔记来自使用者自己选的资料，默认可信，不需要逐条确认，界面不显示。
唯一需要区分的是 2.1 里「模型补充」的内容。

## 3. 非功能需求

- **桌面应用**：用原生窗口包住现有界面，连同后端打包成 exe。开发阶段仍可用浏览器调试。
- **检索**：一两千条时字面匹配加检索词扩展不够用，需要加**向量检索**。向量由服务商的向量接口算，不用本地模型（2026-10-13 确认）；在本机内存里检索，不引入向量数据库。
- **录入队列**要能在应用重启后继续，不能像现在这样只存在内存里。
- 模型接口保持可切换（已有设置页）。

## 4. 明确不做

- 手机端、多设备同步、部署到服务器。
- 浏览器插件或全局快捷键采集。
- 长文档的原文细节问答（不保存全文做分块检索）。
- 出题、闪卡、按大块自动写综述。
- 逐条核实的工作流。

## 5. 与现有设计的冲突（开工前必须先改契约）

现有的 [SCHEMA.md](SCHEMA.md) 和 [TAXONOMY.md](TAXONOMY.md) 是按「保守、人工把关」写的，以下几处与本需求相反：

| 现有规则 | 改为 |
|---|---|
| 分类只能由聚类产生、经人工确认后才写入 `taxonomy.yaml`（不变量 3、SCHEMA §3、TAXONOMY §3–4） | 模型自动写入；使用者的手动改动被锁定 |
| 程序只能新建笔记，不得修改或删除已有笔记（不变量 5） | 使用者可以编辑、删除、合并；录入时发现重复要提示 |
| `verified` 字段，创建时一律 false（§2.2、不变量 11） | 移除 |
| 没有分类的笔记一律进 inbox，等攒够数量再提议（§2.2「inbox 的两种成因」、§3.1 门槛） | inbox 只收模型拿不准的；不再有数量门槛 |
| 模型只转录、不得补充输入里没有的内容（提取提示词） | 允许补充，单独成段标明 |
| 一次输入拆成 1–5 条同质的原子笔记（§2.3、§2.4） | 一条主题笔记加若干概念笔记 |
| 分类提议与人工审批流程（§3.1、`proposals.yaml`、`/api/proposals`） | 不再需要，可删除 |

不受影响、继续有效的：vault 布局与「分类写在 frontmatter、不靠目录」、笔记的稳定 `id`、
原子写入、幂等、「以磁盘为准」、vault 读写必须经过 `app/vault/`、PDF 默认只出一条（与摘要级一致）。

## 6. 开发顺序

| 步 | 内容 |
|---|---|
| 1 | **自动分类和目录树**：录入时归类、自动建块、手动调整并锁定、现有笔记重新归类、目录树加索引页 |
| 2 | **笔记质量和编辑**：主题笔记与概念笔记、流程图和表格的处理、模型补充、完整编辑、重复提示与合并 |
| 3 | **录入队列**（可重启恢复）、**网页链接**和 **PDF** |
| 4 | **关系图谱**和**思维导图** |
| 5 | **多轮追问**和**向量检索** |
| 6 | **打包成桌面应用** |

每一步开工前，先把该步涉及的契约改动写进 SCHEMA.md 并经使用者过目。
