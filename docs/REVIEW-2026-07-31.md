两种收法都合理：(a) 把 `index.db` 声明为 §1 布局里明确的派生物例外，在不变量 1 里写明「`.noteagent/` 下的派生物由 `app/search/` 管理」；(b) 在 `VaultStore` 上加一个 `state_db_path()` 之类的访问器，让 `SearchIndex` 经由它拿路径，把「vault 路径的唯一真相源」收回 `app/vault/`。我倾向 (a)——`SearchIndex` 已经持有 `VaultStore` 并用 `store.state_dir` 取路径（[index.py:57](../backend/app/search/index.py)），路径来源其实已经是收敛的，问题只是契约文字没给这个情况留位置。

除此之外，**`app/` 下没有其它对 vault 的文件 IO**。当前实际合规度很高，风险在于没有任何东西阻止下一次违规。

### 2.2 能否自动守住这条 —— 方案（本轮不写）

三个方案，推荐第一个：

**方案 A：AST 静态检查测试（推荐）**
写一条 `tests/test_invariants.py::test_no_vault_io_outside_vault_module`：用 `ast` 遍历 `app/` 下所有 `.py`，收集对 `open`、`Path.write_text/read_text/write_bytes/read_bytes/mkdir/unlink/rename/replace`、`os.replace/remove`、`shutil.*`、`sqlite3.connect` 的调用节点，凡出现在 `app/vault/` 之外的文件里即失败，用一份显式白名单豁免已知合法项（`extractor.py` 读 prompts、`index.py` 开 index.db——如果 2.1 判定为豁免）。
- 优点：零运行时开销，改坏了立刻红，白名单本身就是「例外清单」的文档，新增例外必须显式加进去（等于强制走一次评审）。
- 缺点：只能抓静态可见的调用，`getattr(Path, "write_text")` 这类绕过抓不到——但那属于蓄意规避，不是这条不变量要防的场景。
- 工作量：约 60 行。

**方案 B：运行时审计钩子**
`sys.addaudithook` 监听 `open`、`os.rename` 等审计事件，在测试夹具里断言：凡是路径落在 vault 根内的，调用栈里必须出现 `app/vault/` 的帧。
- 优点：能抓到动态调用和第三方库的间接 IO（比如 `frontmatter` 库、`yaml` 库自己开文件）。
- 缺点：只覆盖测试实际跑到的路径，覆盖率决定守护力；栈检查有性能开销；`sqlite3` 的 IO 走 C 层不产生 Python 审计事件，恰好抓不到本节唯一的疑点。
- 适合作为 A 的补充，不适合替代。

**方案 C：把 vault 根路径设为私有**
`VaultStore.root` 改成 `_root`，只暴露方法不暴露路径，让 `app/vault/` 之外**拿不到** vault 的绝对路径，从而物理上无法拼出目标。
- 优点：最强，是结构性保证而非检查。

## 5. 接编排层之前的隐患

### H1 —— 并发创建同标题笔记会丢数据（**高**）

- 位置：[store.py:74-80](../backend/app/vault/store.py) `_unique_path` + [store.py:49-54](../backend/app/vault/store.py) `_atomic_write_text`
- 问题：两个独立缺陷叠加。
  1. `_unique_path` 是典型的 check-then-act：`while candidate.exists()` 决定用哪个文件名，返回后才写。并发调用者全都看到「文件不存在」，于是全都选中同一个路径。
  2. `_atomic_write_text` 的临时文件名固定为 `<target>.tmp`。并发写同一个 target 时，多个写者用同一个 tmp 路径，互相踩。
- **实测**（40 线程 barrier 对齐后同时 `create_note("同名笔记")`）：

```
create_note 返回的路径数(去重后): 1
实际落盘文件数              : 1
丢失的笔记数                : 39
残留 .tmp                   : 0
异常: 15 × PermissionError + 19 × FileNotFoundError
```

  异常长这样：
```
PermissionError: [Errno 13] Permission denied: '...\notes\同名笔记.md.tmp'
  at store.py:52 in _atomic_write_text
```
  Windows 上另一个线程持有 tmp 句柄时开同名文件直接 `PermissionError`；另一个线程的 `os.replace` 把 tmp 移走后，其余线程 `FileNotFoundError`。没抛异常的少数线程则**静默覆盖**了彼此——`os.replace` 本身不检查目标是否存在。

- 为什么现在没暴露：目前没有任何并发调用方，`create_note` 只在测试里被单线程调用。编排层一旦并行处理同一批 drafts（同一张截图出的 4 条草稿标题可能撞车），或者两个 ingest 请求同时到达，立刻触发。FastAPI 的同步 endpoint 默认跑在线程池里，这是真实场景。
- 严重程度：**高**
- 建议：
  1. tmp 名加唯一后缀：`target.with_name(f"{target.name}.{os.getpid()}.{uuid4().hex}.tmp")`。这条单独就能消掉全部异常。
  2. check-then-act 换成 try-create：用 `open(path, "x", encoding="utf-8")` 独占创建占位，`FileExistsError` 就递增序号重试，拿到独占后再走原子替换。这条消掉静默覆盖。
  3. 顺带给 `create_note` 加一条并发测试（多线程同标题，断言「落盘文件数 == 调用次数」且内容各不相同），把这条钉死。

### H2 —— 不变量 10 完全没实现（**高**）

- 位置：无（这正是问题）
- 问题：`confidence < 0.6 → 强制 inbox` 在源码里不存在，实测 `0.6` 这个字符串在整个 `app/` 下零出现。编排层马上就要决定每条笔记落 `notes/` 还是 `inbox/`，这是那个决策的核心规则。缺了它，低置信度笔记会直接进正库。
- 一个要注意的交互：[extractor.py:190-197](../backend/app/extract/extractor.py) `_finalize` 在走 `suggested_domain` 路径时把 `confidence` 强制为 `0.0`，而模型层的 cross-field 规则（[models.py:51-53](../backend/app/vault/models.py)）已经保证 `category is None → status must be inbox`。所以「无分类」这一格已经被覆盖了。**真正缺的是「`category` 有值但 `confidence < 0.6`」这一格** —— 模型给了个叶子但自己也不确定。这一格现在会直接落 `notes/`。
- 严重程度：**高**
- 建议：阈值定义成 `app/config.py` 里的常量（契约说「阈值待 eval 校准后确定」，所以要可配）；在 draft→Note 的组装函数里判定并把 `status` 置为 `inbox`。注意此时 `category` 必须一并置 None（否则模型层会因为 `category` 有值而拒绝 `status=inbox`？—— 不，反向规则是「category 为 null 时 status 必须 inbox」，`category` 有值 + `status=inbox` 是允许的）。**但这引出一个契约问题：低置信度落 inbox 时，`category` 该保留还是清空？保留的话 `suggested_domain` 必须为 null，那整理循环就拿不到聚类线索了。待确认。**

### H3 —— index.db 的连接管理与事务边界（**中**）

- 位置：[index.py:59-69](../backend/app/search/index.py) `connect`
- 问题三点：
  1. **写笔记和写索引不在同一个事务里**，也没有失败补偿。`create_note` 成功、`upsert_note` 失败 → 文件在、索引没有 → 搜不到但文件存在。目前靠 `rebuild_all` 兜底，但没有任何东西触发它。编排层需要明确策略：每条写完立刻 upsert（失败则整条回滚删文件？但不变量 5 说录入循环不能删），还是整批写完统一 upsert（失败则标记需重建）。
  2. **没开 WAL、没设 `busy_timeout`**。默认 journal 模式下并发写会直接 `sqlite3.OperationalError: database is locked` 而不是等待。每次操作开新连接（这个设计本身是对的，为了「index.db 随时可删」），但连接多了锁竞争更明显。
  3. `connect` 是 `@contextmanager` + `yield` + `conn.commit()`，**异常路径下没有显式 `rollback()`**。`finally` 里只 `close()`。SQLite 在 close 时会隐式回滚未提交事务，所以不会写坏数据，但 `rebuild_all` 中途失败时会留下一个「已 DELETE 全部、只插了一半」的中间态被回滚——行为正确但不显式，读代码的人看不出来。
- 严重程度：**中**
- 建议：`connect` 里 `PRAGMA journal_mode=WAL` + `PRAGMA busy_timeout=5000`，加显式 `except: conn.rollback(); raise`。编排层的策略选哪种需要你定。

### H4 —— 错误传播路径没有分层（**中**）

- 位置：[extractor.py:38](../backend/app/extract/extractor.py) `ExtractError`、[extractor.py:220-228](../backend/app/extract/extractor.py) `_invoke_structured`
- 问题：`_invoke_structured` 用 `except Exception` 吞掉一切并统一「重试一次」。这把三类完全不同的失败混成了一类：
  - **可重试的瞬时故障**：网络超时、连接重置、429 限流 —— 应该指数退避、重试多次
  - **不可重试的配置/权限故障**：401 密钥错、余额不足、模型名不存在 —— 重试毫无意义，且重试会让真正的原因更难看清
  - **业务降级**：结构化输出解析失败、分类不合法 —— 重试一次合理，失败后应降级落 inbox 而不是让整个 ingest 失败
  现在三者都变成同一个 `ExtractError`，消息里只有 `最后一次: {last}`。编排层拿到它无法决定「重试 / 放弃 / 降级」，只能一律失败。而且 401 会被重试一次再报成「结构化输出解析失败」，与真实原因南辕北辙。
- 另外 `classify` 在拿不到合法 `suggested_domain` 时抛 `ExtractError`（[extractor.py:105-109](../backend/app/extract/extractor.py)），这是**业务降级失败**，与「解析失败」共用一个异常类型，编排层区分不了。
- 严重程度：**中**
- 建议：拆成 `ExtractTransientError`（可重试）/ `ExtractConfigError`（不可重试，直接冒泡到 API 层报 500 + 明确原因）/ `ExtractDegradedError`（降级，编排层落 inbox）。`_invoke_structured` 里按异常类型分流，不要裸 `except Exception`。这个改动最好在编排层动笔之前做，之后改要动所有调用点。

### H5 —— input_hash 该在哪一层算：建议在 API 边界（**中**，含待确认项）

- 位置：目前无实现
- 分析：不变量 8 说「ingest 前先算输入 SHA256」。**建议在 `POST /api/ingest` 收到请求体之后、进编排层之前算**，理由：
  - 进了编排层，输入已经被 [extractor.py:286-295](../backend/app/extract/extractor.py) `_extract_messages` 加工过（base64 编码、拼接 system prompt）。对加工后的产物算 hash，**prompt 一改所有历史 hash 全部失效**，幂等表直接报废。
  - 幂等语义应该是「同一份用户输入」，不是「同一次模型调用」。用户重复上传同一张截图应该命中，即使这期间 prompt 改过。
  - API 边界拿到的正是原始 bytes / 原始文本，最稳定。
- 建议的 hash 输入：`sha256(kind + "\0" + (text or file_bytes))`。
- **待确认（两个我不替你定的点）：**
  1. **`filename` 要不要进 hash？** 同一份 PDF 换个文件名重新上传，算同一次输入（跳过）还是新输入（重跑）？我倾向不进——内容相同就是同一次输入，文件名只是元数据。但如果你希望「讲义_v2.pdf」即使内容没变也重跑，那就要进。
  2. **命中 `ingest_log` 后返回什么？** 契约说「直接返回已有结果」，`result` 列存的是 `{created: [path], skipped: bool}`。但如果那些 path 对应的笔记已经被整理循环改名或归档了，返回的是过期路径。要不要在返回前校验路径仍存在？
- 严重程度：**中**

### H6 —— taxonomy.yaml 缺失或为空会让 API 500（**中**）

- 位置：[taxonomy.py:20-27](../backend/app/vault/taxonomy.py) `load`（`self._path.stat()` 无保护）
- **实测**（临时 vault，只建目录不建 taxonomy.yaml）：

```
taxonomy.yaml 缺失时:
  GET /api/search?q=x             -> 200
  GET /api/search?category=a/b    -> 500
  GET /api/taxonomy               -> 500
  GET /api/inbox                  -> 200
  GET /health                     -> 200

taxonomy.yaml 为空文件时:
  GET /api/taxonomy               -> 500
  GET /api/search?category=a/b    -> 500
```

  不带 `category` 的 search 不受影响，因为 `is_valid_category` 对 falsy 值提前 `return False`（[taxonomy.py:40-41](../backend/app/vault/taxonomy.py)），压根没碰文件。
- 问题：契约 §3.5 说「允许完全为空」，指的是 `categories: {}`；但**冷启动新建一个 vault 时这个文件很可能压根不存在**，那时不是「空 taxonomy」而是 `FileNotFoundError`。空文件（0 字节）也不行——`yaml.safe_load` 返回 `None`，`Taxonomy.model_validate(None)` 抛 `ValidationError`。编排层每处理一条笔记都要读 taxonomy 拿 leaves，这个异常会让整个 ingest 失败，而不是优雅地退化成「全部落 inbox」。
- 严重程度：**中**
- 建议：`load()` 在文件不存在或解析为 `None` 时返回一个空 `Taxonomy`（`version=1, categories={}, tags=[]`），而不是抛。这与契约 §3.5「空 taxonomy 是正常的冷启动状态，不是错误」一致。注意 mtime 缓存也要相应处理（文件不存在时 `stat()` 就抛了，缓存键需要换个写法）。

### H7 —— search 的 `IN (?)` 展开无上限（**低**）

- 位置：[query.py:116-123](../backend/app/search/query.py) `_fetch_rows`、[query.py:148-159](../backend/app/search/query.py) `_recall_fts`
- 问题：`_recall_fts` 对 `MATCH` 结果不设 `LIMIT`，全部塞进 hits；`_fetch_rows` 再把所有 path 展开成 `IN (?, ?, ...)`。同理 [query.py:43-44](../backend/app/search/query.py) 的浏览路径 `SELECT path FROM notes` 也是全表。
- 实测本机 `SQLITE_LIMIT_VARIABLE_NUMBER = 32766`（sqlite 3.53.1），所以要 3 万多条命中才会炸——短期完全不是问题。但 trigram 分词对短查询词（2–3 字）召回率很高，库大了之后每次搜索都会把大半个库读进内存排序。
- 严重程度：**低**
- 建议：现在记一笔即可。真要处理，把排序下推到 SQL（FTS 侧 `ORDER BY bm25 LIMIT n`），或者对 hits 分批 fetch。

### H8 —— TaxonomyManager 的 mtime 缓存在并发/高频写下不可靠（**低**）

- 位置：[taxonomy.py:20-27](../backend/app/vault/taxonomy.py)
- 问题：`self._cached` / `self._cached_mtime_ns` 无锁，多线程同时 `load()` 可能并发解析（结果正确但重复做功）。更实际的是精度问题——测试里是手动 `os.utime(..., mtime_ns + 1_000_000)` 强行推进 1ms 才触发失效的（[test_taxonomy.py:40](../backend/tests/test_taxonomy.py)），说明作者也知道自然写入未必改变 mtime_ns 到可分辨的程度。阶段 4 整理循环写完 taxonomy 立刻读，有概率读到旧值。
- 严重程度：**低**（阶段 4 才有写方）
- 建议：整理循环写 taxonomy 后显式调一个 `invalidate()`，不要依赖 mtime 自动发现。

### H9 —— `VaultStore` 内部 root 解析不一致（**低**）

- 位置：[store.py:44-47](../backend/app/vault/store.py)（`_resolve` 用 `self.root.resolve()`）、[store.py:94](../backend/app/vault/store.py)（`read_note` 用 `relative_to(self.root.resolve())`）vs [store.py:121](../backend/app/vault/store.py)、[store.py:139](../backend/app/vault/store.py)、[store.py:149](../backend/app/vault/store.py)（`create_note` / `write_moc` / `save_asset` 用 `relative_to(self.root)`，**未 resolve**）
- 问题：如果传入的 root 含 `..`、是符号链接、或是 Windows 8.3 短名，`self.root` 与 `self.root.resolve()` 不相等，`relative_to` 会抛 `ValueError`。目前 `default_vault_root()` 产出的是干净绝对路径，测试用的是 `tmp_path`，都不触发。编排层如果从配置读一个用户填的路径（`VAULT_PATH` 环境变量就是这么一条口子），就可能踩到。
- 严重程度：**低**
- 建议：`__init__` 里一次性 `self.root = Path(root).resolve()`，后面全部用它。
